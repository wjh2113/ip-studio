## 2. 当前技术栈与理由

| 层 | 用的 | 为什么选它 | 放弃了什么 |
|---|---|---|---|
| 语言 | JavaScript（Node.js ≥ 22），前后端一种语言 | 一个人能前后端通吃；部分代码前后端共用（`shared/place.js`）；流式输出天生擅长 | Python 的 AI / 数据生态（需要时另起小服务，见 §5） |
| 前端 | Vue 3 + Pinia + Vite | 国内最主流、最好招人；模板写法和原来的 HTML 最接近，迁移成本最低；将来能用 uni-app 出小程序 | React 更大的全球生态、React Native |
| 后端框架 | Fastify 5 | 轻、快、自带参数校验和日志；从原生 `node:http` 迁过来改动最小 | NestJS 的严格分层（团队大了再考虑） |
| 数据库 | PostgreSQL + Drizzle ORM | 多进程并发、事务、全文检索、将来的 pgvector；Drizzle 轻，SQL 可控 | SQLite 的零运维（单进程时它很好，但扩不了） |
| 任务队列 | Redis + BullMQ | 出图、口播评测要几十秒到几分钟，不能挂在请求上；BullMQ 是 Node 生态最成熟的队列 | 进程内队列（重启丢任务、不能多实例） |
| 模型调用 | 官方 SDK + 自研 `server/llm.js` | 要自己控计费、额度、分档、超时、用量统计、A/B；LangChain 管不了这些，还多一层抽象 | LangChain 的现成组件 |
| 文件 | 服务器本地 `data/` | 起步最简单 | 多机、CDN（计划迁对象存储） |
| 部署 | nginx + pm2 + `scripts/deploy-jdcloud.sh` | 一台机器、一条命令 | 容器化（Docker / K8s，规模上来再做） |
| 测试 | `node:test` + 接口冒烟 + Playwright 浏览器回归 | 零额外框架；接口和浏览器测试拦住单测看不到的问题 | Jest / Vitest（没必要） |

### 2.1 为什么后端不用 Python 或 Java

- **瓶颈在模型调用**：一次成稿等模型几秒到几十秒，服务器自己的处理只有几毫秒；换语言用户感觉不到差别。
- **Node 更适合流式成稿和大量长连接**；性能上 Node 也比 Python 快，比 Java 省资源。
- **生成效果和语言无关**：取决于模型、提示词、输出校验。
- Java（Spring Boot）对这个规模偏重：代码量翻倍、启动慢、吃内存；只有卖给要求 Java 技术栈的企业、或对接企业 Java 系统时才值得。
- Python 在「服务器上自己做重活」时更强（语音、视频、数据分析、本地模型），这部分按 §5 以小服务的方式加，不替换主服务。

### 2.2 为什么不用 LangChain

`llm.js` 已经做了 LangChain 在本项目里能提供的价值（多模型切换、快慢分档、重试、超时），还带着它做不了的：额度预扣与结算、中断按已生成部分计费、每人并发上限、用量与提示词变体记录。引入 LangChain 会打破「少依赖」、多一层难排查的抽象、版本变化快，计费需要的准确 token 数也不一定拿得全。

**LangGraph 留作将来**：做「热点 → 选题 → 写稿 → 检查 → 不合格自动重写 → 人工确认」这类多步自动化流水线时，用 LangGraph.js 编排流程，每一步调模型仍走 `llm.js`。

## 3. 现状与已知取舍（2026-10）

### 3.1 前端：已全部是 Vue

- 2026-10 迁完：应用、管理后台、提示词说明书、落地页、营销页都是 Vue 3 + Pinia，Vite 多入口构建；原来 `public/` 下按 id 拼 HTML 的脚本（约 4700 行、110 处 `innerHTML`）已删除。目录和约定见 `docs/ARCHITECTURE.md` 的「前端」。
- 数据按业务拆成十几个 store（账号、简报、成稿区、口播、配图……），组件只管界面。插图位置算法 `shared/place.js` 前后端共用一份。
- 迁移顺手修掉的线上问题：`#cw > *` 样式把浮层、提示条、提词器的 `position: fixed` 压成了 relative（浮层会跑到页面最底下）；配图栏里改过的画面提示词出图时没带上；离开一篇稿子时没存的改动可能写到下一篇。
- 回归测试：`tests/ui/` 下 13 个浏览器流程（`npm run test:ui`），覆盖登录、账号设定、简报、成稿区、口播、配图、多平台、导出、任务中心、用量与支付、后台、独立页面。

### 3.2 单实例假设

以下在「一台机器、pm2 单实例」下没问题，起第二个实例前要改：

| 位置 | 现状 | 多实例时要改成 |
|---|---|---|
| `server/limit.js` 限流 | 进程内计数 | Redis 计数（INCR + 过期） |
| `server/jobs.js` 每人并发上限 | 进程内计数，超了延后 3 秒、有人让出名额立刻提前 | Redis 计数或 BullMQ Pro 分组；或按用户分队列 |
| `server/jobs.js` 同步等结果（`waitFor`） | 进程内回调 | QueueEvents 或轮询数据库 |
| `server/llm.js` 每人同时 3 个生成 | 进程内计数 | Redis 计数 |
| 文件 | 本地 `data/` | 对象存储 |

### 3.3 刻意保留的默认值

| 行为 | 原因 | 要改怎么改 |
|---|---|---|
| 生产环境没配真实支付时收不了钱，演示支付也关着 | 防止前端拿演示回调白开套餐 | 接好微信 / 支付宝；验收时临时 `PAY_ALLOW_MOCK=1`。启动日志会提示 |
| 管理后台只认 `ADMIN_PASSWORD`，不用访问密码兜底 | 后台权限和访问门禁分开 | `.env` 配 `ADMIN_USERNAME` / `ADMIN_PASSWORD`（≥ 8 位）；没有管理员时启动日志会提示 |
| 部署脚本在生产环境把注册关了（设 `REGISTER_OPEN=0`；代码默认是开的） | 先内部使用 | 开放时设 `REGISTER_OPEN=1`（同时没有 `ACCESS_PASSWORD`） |
| 正文历史：自动保存 10 分钟一版、每篇最多 50 版 | 控制库大小 | `REVISION_GAP_MIN`、`REVISION_MAX` |

### 3.4 命名

产品名**自媒体助手**（界面、文档、订单）；内部标识 **ip-studio**（目录、`package.json`、pm2、`/health` 的 `app`、队列名；Redis 键前缀是 `ipstudio:<库名>`）；域名 `ip.aidigitcloud.cn`。旧名「文案工坊」「copywriter-studio」已停用。

## 4. 本项目专有的编码规矩

通用规范见 `NEW-PROJECT-TECH-GUIDE.md` 第 9～12 节（分层、编码、注释、AI 助手清单）。下面是这个项目特有的：

- **新接口**：`server/index.js` 的 `ROUTES` 加一行，处理函数写在 `server/routes/<域>.js` 并 `export`；在 `tests/routes.test.js` 补一条真实 HTTP 测试。
- **改表**：只在 `server/migrations.js` 末尾追加编号迁移，同步 `server/schema.js`；迁移要考虑线上已有数据（参考迁移 2：先合并重复、退回预扣，再加唯一索引）。
- **模型功能**：同时在 `llm.js` 的 `FEATURE_TIER` 定档、`plans.js` 的 `TEXT_FEATURES` 登记、`promptrev.js` 和 `promptdocs.js` 登记提示词。
- **额度**：`reserve` → `settle`，不要先查后扣；长任务里用 `ctx.hold` / `ctx.settle`。
- **长任务**：`jobs.js` 的 `defineJob` / `enqueue`；任务状态以 PostgreSQL 为准，Redis 只放任务号。
- **模型输出**：引用原文的字段要能逐字找到，结构不全重试一次，不信分数和金额；外部内容进提示词用 `fence`。
- **出镜评测**：整段视频交给网关，不在本地抽帧；语种按稿子判断，转写、发音、出镜用同一个语种。
- **前端**：遵守 §3.1 的迁移规则；拼 HTML 先 `esc()`；不用原生 `alert` / `confirm`。
- **检查**：`npm test`（含 `scripts/check-async.js` 异步检查）全绿才提交；界面改动跑 `npm run test:ui`。

## 5. 什么时候引入 Python

主服务保持 Node。下面这些要在服务器上「自己算」的功能，用一个只在内网被调用的 **Python + FastAPI 小服务**来做，耗时的走现有任务队列（Node 登记任务、worker 调 Python、结果写回库），计费和任务中心全部复用：

| 优先级 | 功能 | 现在 | 用 Python 后 | 常用库 |
|---|---|---|---|---|
| 1 | 素材召回 | 字面关键词 | 按意思匹配 | bge-m3 等中文向量模型 + pgvector |
| 2 | 文件导入（范文、旧文章、语气样本） | 只能粘文字 / txt / md | 直接传 Word、PDF、截图 | python-docx、pdfplumber、PaddleOCR |
| 3 | 口播细节分析 | 网关打分 | 语速、停顿、口头禅、音量，精确到秒 | librosa、parselmouth |
| 3 | 本地转写（可选）、口播自动加字幕 | 网关 / 无 | 省钱、逐字时间戳、导出成片 | FunASR、Whisper、ffmpeg |
| 4 | 复盘多因素分析 | 分组比中位数 | 各因素各自影响多大 | pandas、statsmodels |
| 4 | 防洗稿升级 | 连续 8 字相同 | 识别换词、调语序 | jieba + SimHash / 向量相似度 |

不搬到 Python 的：调大模型和流式成稿、登录计费支付、任务队列本身。

如果将来团队主力换成 Python、后端改动频繁，再按「新功能用 Python 写 → nginx 按路径分流 → 共用数据库和登录态 → 旧接口按模块逐个搬 → 搬完下线 Node」的顺序迁移，不一次性重写。

## 6. 移动端

### 6.1 路线

**现状（2026-10）**：网页迁完 Vue 之后直接走了 2b，`mobile/` 是 uni-app 工程，一套代码出 H5、App、微信小程序，第一版已覆盖 §6.2 的全部功能（只做页面，推送未接）。
服务端只为它加了 Bearer 登录和几条聚合接口（`server/routes/mobile.js`、`/api/transcribe`），见 ARCHITECTURE「移动端接口」。下面的阶段表保留作当时的选型依据。

| 阶段 | 做法 | 复用 | 说明 |
|---|---|---|---|
| 1 | H5 / PWA：现有网页做好窄屏适配 | 几乎全部 | 最快；样式已有多处窄屏断点，提词器和录音已能在浏览器里用 |
| 2a | Capacitor 打包成 App | 几乎全部（旧 DOM 代码也能跑） | 能用原生相机、录像、推送 |
| 2b | uni-app 出微信小程序 + App | 只复用真正的 Vue 组件和纯逻辑模块 | 小程序没有 DOM，要先完成 §3.1 的迁移 |
| 3 | React Native | 只复用后端接口 | App 成为主打、有专人负责时 |

面向公众上线生成式 AI 服务（尤其小程序、应用商店）有备案、内容安全等合规要求，立项前先确认。

PWA 是什么、能做什么，见 [NEW-PROJECT-TECH-GUIDE.md §8.1](NEW-PROJECT-TECH-GUIDE.md)。本项目**目前还不是 PWA**（没有 manifest 和 Service Worker），做第 1 阶段时要补：

1. `web/public/manifest.webmanifest`：名称「自媒体助手」、图标（192 / 512 px）、`display: standalone`、主题色；`web/index.html` 里加 `<link rel="manifest">` 和 `apple-touch-icon`。
2. Service Worker 只缓存静态资源（`/`、`/assets/*`、图标），**不缓存任何 `/api/*`**：接口涉及额度、登录态和流式输出，缓存会出错。离线时显示「没有网络」页即可，不做离线写稿。
3. 版本更新：`/assets/*` 文件名带哈希，SW 用「先网络、失败再缓存」处理 `/`，避免用户卡在旧版本。
4. 窄屏检查：创作记录侧栏改抽屉、弹窗全屏、编辑器工具栏收起；提词器加屏幕常亮（Wake Lock）。
5. 推送（任务完成、数据回填提醒）：安卓 Chrome 可用；iPhone 要 iOS 16.4+ 且先「添加到主屏幕」；**微信内置浏览器不支持安装和推送**——国内用户多从微信打开链接，所以提醒还要有站内消息兜底。

### 6.2 功能范围

| 优先级 | 功能 | 为什么适合手机 |
|---|---|---|
| ★★★ | 口播录制 + 提词器（**录视频**，现在网页只录音；前置摄像头、滚动提词、防息屏，录完走任务队列） | 口播本来就用手机拍 |
| ★★★ | 口播评测结果（分数、点回对应句子、完成推送） | 拍完马上看、马上重拍 |
| ★★★ | 灵感和素材随手记（语音 / 文字 / 拍照 → 选题池、素材库） | 灵感在碎片时间出现 |
| ★★☆ | 热点速览 → 一键存选题池 | 刷热点是手机行为 |
| ★★☆ | 快速出稿（题材 → 方向 → 成稿，读和轻改，一键复制去发） | 通勤出短稿 |
| ★★☆ | 按住说话改稿 | 手机打字慢 |
| ★★☆ | 发布数据回填（第 1、7 天推送提醒）+ 只读复盘 | 发完在手机上看数据 |
| ★☆☆ | 任务中心、配图保存到相册、标题候选挑选、快速建号 | 轻操作 |

留在电脑上：长文精细编辑、多平台版本对照、框架库编辑与范文拆解、完整账号设定、语气样本管理、管理后台、提示词与 A/B、导出 Word / PDF。

第一版建议：**口播录制与评测 + 灵感速记 + 热点存选题 + 快速出稿（读和复制）+ 数据回填**，先用 H5 验证使用频率。

实际第一版（`mobile/`）在此之外还做了：语音改稿、审稿卡片、发布包、标题候选、对标速存、快速建号、喂语气样本、内容日历、一键切账号、存相册。
热点速览暂未放进 App。还没做的：App 端边提词边录视频（要 nvue `live-pusher`，现在 App 只录音，H5 和小程序能录视频）、
系统「分享到」入口（安卓 intent-filter / iOS Share Extension）、推送（提醒先显示在「今天」页）、手机上买套餐。

## 7. 重新评估的触发条件

| 触发条件 | 重新考虑 |
|---|---|
| 要在服务器上跑语音、视频、数据分析、本地模型 | 加 Python + FastAPI 小服务（§5） |
| 团队主力换成 Python，后端改动频繁 | 逐步迁 Python（§5 末尾） |
| 团队超过 5 人、模块边界经常打架 | 后端 NestJS，前后端上 TypeScript |
| 要做微信小程序 | `mobile/` 已是 uni-app，补小程序 appid、合法域名和类目资质后 `build:mp-weixin` |
| App 成为主打产品 | React Native 或原生 |
| 要做多步自动化创作流水线 | LangGraph.js（模型调用仍走 `llm.js`） |
| 单机扛不住、要起第二个实例 | 按 §3.2 把进程内计数挪到 Redis，文件上对象存储 |
| 企业客户要求 Java | 评估 Spring Boot 对接层 |
